# Atlas Rush Results Implementation Instructions

Implement automatic local result history, optional display names, a responsive progress dashboard, and server-rendered links for individual results. The player can finish and replay a game without entering a name. A recipient can read a shared result on another device with JavaScript disabled.

Read [AGENTS.md](../AGENTS.md), [REACT.md](../REACT.md) and [DESIGN.md](../DESIGN.md) before editing. Use the [product proposal](atlas-rush-results-proposal.md) as design context. Keep work in Atlas Rush and reuse its gameplay, challenge URL and session persistence code. This release uses an IndexedDB history and a share URL that carries one result. Accounts, synced history, leaderboards and revocable links are outside its scope.

## 1 Persist finished attempts

- Extend the existing `atlas-rush` database in [database.ts](../src/games/atlas-rush/infrastructure/persistence/database.ts). Bump the IndexedDB version from 1 to 2. On a fresh install, create both stores. On upgrade, keep the existing `sessions` store and records and add `results`, keyed by `attemptId`, with a `finishedAt` index. Preserve the guarded open and `versionchange` handling. A blocked or unavailable database should still allow play.
- Define a typed result record with `attemptId`, `finishedAt` (epoch milliseconds), the `GameResults` snapshot, and optional `displayName`. Keep the original result counts and fractional elapsed seconds. Add repository operations to read one result, list newest first, update or clear the name, and delete a single result. Read and write through `idb` and report success after the transaction commits.
- Use a new identifier for each new round, including another play of the same seed. Keep the ID on the persisted session record and reuse it on Continue, even when the tab ownership `generation` changes. Give a valid version 1 session its first ID inside the successful claim when resumed. Preserve compatibility with version 1 records that lack the field. Start history with newly finished rounds and leave previous finished checkpoints in their existing lifecycle. [Session record format](../src/games/atlas-rush/infrastructure/persistence/snapshot.ts)
- Handle the transition to `finished` once through the persistence layer. Capture the result through `getResults` and capture the finish timestamp once. Save both terminal outcomes, including zero coverage. An unfinished round abandoned through **End game** adds no entry. Observe the transition for rounds that start in memory as well as persisted sessions, so the report and a retry are available either way. [Result calculation](../src/games/atlas-rush/domain/results.ts), [Current persistence hook](../src/games/atlas-rush/hooks/useSessionPersistence.ts)
- For an owned session, process finalization behind pending checkpoint writes. In one read/write transaction spanning `sessions` and `results`, verify ownership and revision and commit the final checkpoint and result together. Keep the existing request and transaction rejection handling. An already committed attempt is a successful retry and must retain its first timestamp and any edited name. A stale tab must never overwrite an owned session or add a competing result for the same attempt. For a round that started without a persisted session, retry by opening storage and inserting the result under the same ID. Keep session discard and replay independent of result deletion. [Session repository](../src/games/atlas-rush/infrastructure/persistence/session-repository.ts)

## 2 Update the mission report

Use `AtlasRushResults` from the current Storybook work if it is available on the branch. Otherwise extract the existing full-screen results dialog from `AtlasRush`. Reuse the report body in the game, the dashboard detail view and the shared result view. Keep it separate from modal behavior and navigation so the shared route can render it without a client island. Preserve existing headings, labels, replay behavior and settings restoration. [Gameplay entry point](../src/games/atlas-rush/components/AtlasRush.tsx), [Report panel](../src/react-component-library/ResultsPanel.tsx)

- Show the report immediately. Display an accessible status for saving, **Saved on this device**, and failure with **Retry save**. Keep the report and sharing available if IndexedDB fails. Give a pending write a chance to finish before **Play again**, **Start over**, or **My results** navigates. Give the player a clear way to leave if saving fails.
- Add **Display name** and **Save name**. Use the same validation in the mission report, dashboard and share code. Trim whitespace, treat an empty value as clearing the name, and accept at most 32 Unicode code points. Save the name to the selected result alone. Keep initial dialog focus on a button and keep the name field usable with the mobile keyboard open.
- Add **Share result** and **My results**. Keep gameplay and navigation callbacks outside the reusable presentation component. Storybook stories should use fixtures for completed, timed out, saving, storage failure and narrow mobile layouts, without opening IndexedDB or navigating away. Put the stories under `src/react-component-library/`, where the existing config discovers them.

## 3 Build My results

Add `src/pages/games/atlas-rush/results/index.astro` and a game-owned React dashboard. Hydrate the browser storage reader on the client. Add a **My results** link to the settings page and mission report. Use the Atlas Rush top bar and shared tokens with a naturally scrolling page. The gameplay shell’s fixed height and overflow rules are specific to gameplay.

- Show a table on wider screens and stacked cards on compact screens. Sort newest first. Include date, region, difficulty, mode, guessed out of total, coverage and elapsed time. Provide a detail view with the name, finish reason and shared report body. Let players edit the name, share the result or delete it after confirmation. Update the visible history after a successful edit or deletion.
- Start history with all attempts. Offer filters for region, difficulty, Learning mode and full-name or Speed mode. Give the progress section its own **Progress for** selector. Default to the group from the newest result. Group by region, difficulty, Learning mode, answer mode and prefix length, and challenge rules version. Treat a legacy missing answer mode as full-name. Seeds identify individual challenges and are excluded from progress grouping.
- For the selected group, show attempts, best coverage, fastest completion, and up to 10 recent attempts in chronological order on a 0–100% coverage chart. Use only completed rounds for fastest completion and show a placeholder when there is none. With one result, show the score and a short prompt to play again. Provide a text summary along with the chart.
- Include loading, empty, filtered-empty and storage-unavailable states. The empty state links to **Start survey**. Use semantic controls and confirm the result detail and history are usable at 320px wide and in short landscape layouts.

## 4 Render shared results on the server

Add `src/pages/games/atlas-rush/results/shared/[token].astro` for `/games/atlas-rush/results/shared/v1.<token>/`. Use the Astro 5 compatible Cloudflare adapter and opt this route out of prerendering. Keep static output as the default. Use the host’s server runtime for this route and verify it is routed to the server function in deployment preview. For Cloudflare Pages, use the Astro 5 adapter generation that supports Pages and check the generated routing. [Current Astro config](../astro.config.mjs), [Astro 5 rendering](https://v5.docs.astro.build/en/guides/on-demand-rendering/), [Cloudflare Pages routing](https://v5.docs.astro.build/en/guides/integrations-guide/cloudflare/#routing-on-cloudflare-pages)

- Implement a codec used by both the share control and the server route. Use UTF-8 JSON with unpadded base64url for v1. The token is a path segment. Write an explicit allowlist of fields for challenge version, region, difficulty, Learning mode, normalized answer comparison, seed, correct count, total, elapsed seconds, finish reason and an optional display name. Derive coverage and not-guessed count from the validated counts. MessagePack can be a separate format version if measured URL lengths justify it. [Base64url specification](https://www.rfc-editor.org/rfc/rfc4648#section-5)
- Reject an unknown format version, malformed encoding or token longer than 1,024 characters before JSON parsing. Validate required fields, known region and level, answer settings and seed with existing validators, positive integer total, integer correct between zero and total, finite nonnegative elapsed time, and consistency of finish reason with the counts. Use the token’s stored total when checking the score so later map edits do not invalidate it. Return a readable 404 for an invalid token and link back to Atlas Rush. Render valid reports from older rules versions through a display model that preserves the version. Show **Try this challenge** only when the current game supports it.
- In the share UI, show which data will leave the browser and default **Include display name** to off. Build the link with the active site origin and offer manual copying if the clipboard fails. Leave out the local attempt ID, finish timestamp and other rounds. The link is readable by anyone who receives it, and deleting local history leaves distributed links intact.
- Render the full read-only report and **Unverified result** in the first HTML response. Use an ordinary link generated with `getChallengePath` for **Try this challenge**. Render any display name as text and leave it out of Open Graph metadata. Use a result-specific title and score description with the existing shared image and a `noindex` directive. Viewing this route must neither read nor write the visitor’s IndexedDB. [Challenge URL helper](../src/games/atlas-rush/infrastructure/challenge-url.ts), [Page metadata layout](../src/layouts/GameLayout.astro)

## Acceptance criteria and handoff

| Scenario                       | Expected outcome                                                                                                                                                                                                                                                                        |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Existing version 1 database    | The new store appears, unfinished sessions still resume, and a resumed round produces one result.                                                                                                                                                                                       |
| Finish, retry, and replay      | Both terminal reasons save automatically. Retrying or refreshing leaves one row with its original timestamp and name. A new round on the same seed creates a second row. An abandoned round creates none.                                                                               |
| Two tabs or failed storage     | Only the owning tab finalizes a saved attempt. When no local save is possible, the result remains readable and shareable.                                                                                                                                                               |
| History and name management    | Results survive reload. Name edits and deletion affect the selected local result. Progress compares like rules, and a timeout cannot set the fastest completion.                                                                                                                        |
| Responsive and keyboard review | Table and cards expose equivalent history. At 320px there is no horizontal page scrolling. Report actions remain reachable with the mobile keyboard open, and dialog focus is visible.                                                                                                  |
| Shared result                  | A plain HTTP request returns the score in the first HTML response. The report is readable in a separate browser profile with JavaScript disabled. Anonymous links contain no name. A malformed token receives the error view. The challenge link preserves the original rules and seed. |

Add focused regression coverage for the database upgrade and finalization, progress grouping, the share codec, and server response HTML. Follow the repository verification policy. Run tests, TypeScript, ESLint, Prettier checks or builds only when the user explicitly asks. Hand back the affected routes, Storybook entries, and any preview or device checks that still need the user’s review.
